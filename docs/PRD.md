## 1. 제품 개요

### 1-1. 한 줄 정의

전북대 덕진구 생활권의 학생들이 한 가게에서 함께 주문해 최소주문금액을 채우고 배달비 부담을 나눌 수 있도록 연결하는 공동주문 모바일 웹 서비스.

### 1-2. 배경

자취생·기숙사생 등 1인 가구는 배달 음식을 주문할 때 다음 문제를 반복해서 겪는다.

- 혼자 먹을 양보다 최소주문금액이 높아 주문을 포기하거나 필요 이상으로 주문한다.
- 최소주문금액을 맞추더라도 한 사람이 배달비를 전부 부담한다.
- 주변에 함께 주문할 사람이 있어도 서로를 찾을 수단이 없다.
- 기존 커뮤니티에서는 공동주문 글이 다른 게시물 사이에 묻히고, 모집 상태와 참여자를 체계적으로 관리하기 어렵다.
- 맛집 추천이나 같이 먹을 사람을 찾는 대화가 여러 채널에 흩어져 있다.

**시장 공백 요약**

> 배달의민족 '함께주문'은 이미 아는 사람에게 링크를 공유하는 방식이다.
> **주변에 지인이 없는 1인 가구가 모르는 인근 학생과 주문 직전에 매칭되는 창구**는 비어 있다.

### 1-3. 제품 가설

전북대 인근이라는 좁은 생활권 안에서 현재 모집 중인 주문을 빠르게 보여주고 참여 신청부터 주문 채팅까지 연결하면, 학생들은 혼자 주문할 때보다 적은 비용으로 원하는 음식을 주문할 수 있다.

### 1-4. AI 활용 원칙

- 생성형 AI는 UI 작성, 코드 생성, DB 설계, 테스트 작성, 오류 분석 등 **개발 과정**에 활용한다.
- AI가 생성한 코드는 팀원이 직접 실행·검토한 뒤 반영한다.
- **API 키, DB 연결 문자열, 개인정보를 공개형 AI 입력창에 넣지 않는다.**
- 음식 추천·자동 매칭 같은 **사용자 대상 AI 기능은 MVP에 포함하지 않는다.**

## 2. 문제 정의

### 2-1. 핵심 문제

> 전북대 인근에서 혼자 생활하는 학생은 최소주문금액과 배달비가 부담되지만, 같은 시간대에 같은 가게에서 주문하려는 가까운 사람을 쉽고 안전하게 찾기 어렵다.

### 2-2. 해결해야 할 사용자 과업

1. 지금 참여할 수 있는 가까운 공동주문을 빠르게 찾는다.
2. 원하는 주문이 없으면 직접 모집글을 만든다.
3. 모집자와 참여자가 주문 내용·정산 방법·수령 장소를 대화로 조율한다.
4. 자신이 만든 주문과 참여한 주문의 상태를 다시 확인한다.
5. 전북대 생활권의 음식 정보와 같이 먹을 사람을 커뮤니티 채팅에서 찾는다.

## 3. 제품 목표

### 3-1. MVP 목표

- 덕진구 생활권 안에서 공동주문 모집자와 참여자를 연결한다.
- 모집글 작성 → 참여 승인 → 주문 채팅까지 전 과정을 웹 안에서 이어 준다.
- 공동주문 외에도 음식 추천과 동행을 찾는 기본 커뮤니티 공간을 제공한다.
- 사용자가 자신의 계정과 주문 활동을 직접 관리할 수 있게 한다.

### 3-2. MVP가 검증하려는 것

- 학생들이 실제로 최소주문금액·배달비를 줄이기 위해 공동주문에 참여하는가?
- 스토리처럼 빠르게 훑는 공동주문 목록이 참여 탐색에 도움이 되는가?
- 주문 채팅과 음식 커뮤니티가 재방문 이유가 되는가?

### 3-3. 비목표 (Non-Goal)

- **배달앱을 대체하지 않는다.** 실제 주문은 모집자가 기존 배달앱·전화로 진행한다.
- **결제를 대행하지 않는다.** 금전은 사용자 간 외부 수단으로 처리한다.
- 이 MVP의 책임 범위는 **사람을 연결하고 주문 조율 공간을 제공하는 것까지**다.

---

## 4. 목표 사용자

### 4-1. 1차 목표 사용자

전북대학교 학생 중 덕진구에서 생활하거나 자주 활동하는 1인 주문자

- 전북대 기숙사 거주 학생
- 전북대 인근 자취생
- 학교에서 늦게까지 있어 혼자 식사를 주문하는 학생
- 최소주문금액 또는 배달비 때문에 주문을 망설이는 학생

### 4-2. 2차 목표 사용자

- 학교 주변 맛집 정보를 얻고 싶은 학생
- 함께 식사하거나 새로운 음식을 먹으러 갈 사람을 찾는 학생
- 공동주문을 주도하고 참여자를 모집하려는 학생

### 4-3. 페르소나

**A. 최소주문금액이 부담되는 학생 (참여자형)**
> "야식으로 토스트 2개만 먹고 싶은데 최소주문 15,000원이라 못 시켜."
- 필요: 나머지 금액을 채워줄 사람, 배달비 분담, 지금 바로 참여 가능한 팟

**B. 자주 모집하는 학생 (모집자형)**
> "내가 주문할 건데 같이 시킬 사람?"
- 필요: 빠른 모집, 신청자 승인·거절, 수령 장소 안내, 상태 관리

**C. 정보 탐색형 학생 (커뮤니티)**
> "오늘 뭐 먹지? 이 근처 뭐가 맛있지?"
- 필요: 가벼운 소통, 활성 팟이 없을 때의 재방문 이유

### 4-4. MVP 비대상

- 덕진구 밖의 불특정 지역 사용자
- 일반 중고거래나 모든 종류의 공동구매를 원하는 사용자
- 식당·배달기사 등 사업자 사용자

## 5. 핵심 기능

> 핵심 기능은 **3개로 고정**한다. 5-4의 정산 보조는 P1이며, P0가 전부 끝났을 때만 착수한다.

### 5-1. 핵심 기능 ① — 공동주문 모집 및 참여 (P0)

서비스의 가장 중요한 기능. 모집 중인 주문을 빠르게 탐색하고, 참여를 신청하거나 직접 모집글을 만들 수 있어야 한다.

**공동주문 목록**

- 빠르게 넘겨볼 수 있는 **스토리형 요약 영역** + 카드형 목록을 제공한다.
- 기본적으로 모집 중인 주문을 우선 노출한다.
- 위치 권한을 허용하면 수령 장소까지의 거리를 표시하고 가까운 순 정렬을 제공한다. *(P1)*
- 위치 권한을 거부하면 선택한 **활동 지역** 기준으로 목록을 보여준다.
- 카드 표시 정보: 가게명 / 음식·주문 요약 / 활동 지역·수령 장소 / 모집 마감 시각 / 현재 참여 인원 / 모집 상태

**공동주문 작성**

| 입력값 | 방식 |
|---|---|
| 가게명 | 네이버 지역 검색 API 검색 결과에서 선택 |
| 음식 종류 또는 주문 내용 | 텍스트 |
| 모집 목표 | 필요 인원 **또는** 채워야 할 금액 |
| 모집 마감 시각 | 날짜·시간 선택 |
| 주문 또는 수령 예정 시각 | 날짜·시간 선택 |
| 수령 장소 | 네이버 지역 검색 API·NAVER Maps API 검색 결과 선택 + 직접 설명 추가 |
| 추가 안내 | 텍스트 (선택) |

- 선택한 가게와 수령 장소는 **장소명·주소·위도·경도**를 함께 저장한다.
- 다른 사용자에게는 개인 위치가 아니라 **공동주문에 지정된 공개 수령 장소만** 표시한다.

**참여 신청 및 관리**

- 참여자는 상세 화면에서 짧은 **참여 메시지**와 함께 신청한다.
- 모집자는 신청을 승인 또는 거절한다.
- 승인된 참여자만 해당 주문 채팅방에 입장할 수 있다.
- 거절된 사용자와 미신청 사용자는 채팅방에 접근할 수 없다.
- 모집자는 신규 신청을 막기 위해 모집을 마감할 수 있다.

**상태 전이**

```
모집 중 → 모집 마감 → 주문 완료
              └──────────→ 취소 (주문이 진행되지 못한 경우)
```

### 5-2. 핵심 기능 ② — 주문 채팅 및 음식 커뮤니티 (P0)

채팅 탭은 **내 채팅**과 **음식 커뮤니티**로 구분한다.

**내 채팅 (주문 채팅)**

- 참여가 승인되면 해당 주문의 전용 채팅방이 생성되거나 사용자에게 노출된다.
- 조율 대상: 최종 주문 메뉴 / 개인별 금액과 외부 정산 방법 / 주문 시각 / 수령 장소와 방법
- 메시지에는 작성자 **닉네임**과 작성 시각을 표시한다.
- 새로고침하거나 다시 로그인해도 이전 메시지가 유지되어야 한다.
- 채팅방 상단에 **가게명 · 수령 장소 · 수령 예정 시각**을 고정 표시한다.

**음식 커뮤니티**

에브리타임처럼 전북대 생활권의 음식 대화를 나누는 **고정 채팅방**을 제공한다.

- 맛집·메뉴 추천
- 같이 먹기 / 음식 여행

MVP에서는 **운영자가 정한 고정 채팅방만** 제공하며, 사용자가 임의로 공개 채팅방을 만드는 기능은 제공하지 않는다.

---

### 5-3. 핵심 기능 ③ — 회원 계정 및 마이페이지 (P0)

서비스 전용 계정으로 사용자 활동과 공동주문 이력을 관리한다. MVP에서는 휴대전화·이메일·학교 소속 등 **외부 본인인증을 구현하지 않는다.** 로그인은 사용자를 구분하고 공동주문·채팅 권한을 제어하기 위한 기본 계정 기능으로만 사용한다.

**회원가입 필수 정보**: 아이디 / 비밀번호 / 닉네임 / 활동 지역

**계정 정책**

- 동일한 아이디로 중복 가입할 수 없다.
- 다른 사용자에게는 아이디가 아닌 **닉네임**을 표시한다.
- 로그인 상태를 유지할 수 있고 직접 로그아웃할 수 있다.
- 현재 비밀번호를 확인한 뒤 비밀번호를 변경할 수 있다.
- 외부 인증 수단이 없으므로 **비밀번호 찾기·자동 재설정은 MVP에 포함하지 않는다.**
- 비밀번호는 DB에 평문으로 저장하지 않는다.

**마이페이지**

- 내가 만든 공동주문 목록
- 내가 참여 신청한 공동주문 목록과 승인 상태
- 참여 중이거나 완료된 공동주문 내역
- 닉네임·활동 지역 등 기본정보 수정
- 비밀번호 변경

### 5-4. 보조 기능 — 분담 금액 표시 (P1, 선택 구현)

> **이 기능은 결제·송금이 아니다.** 화면에 숫자를 계산해 보여주는 것까지이며, 실제 이체는 사용자가 외부에서 직접 한다. "서비스 내 결제·송금·자동 정산 없음" 원칙과 충돌하지 않는다.

**왜 남겨두는가**: 제품의 존재 이유가 "돈을 아끼는 것"인데, 얼마를 아끼는지 화면에서 보이지 않으면 참여 판단이 어렵다. 다만 P0 3개를 위협하면 안 되므로 **선택 구현**으로 둔다.

**계산 규칙**

```
개인 부담금 = 개인 주문 금액 + (배달비 ÷ 참여 확정 인원)
```

- 음식 값은 **각자 입력값 그대로** 사용한다. 음식 값까지 1/N 하지 않는다.
- 배달비만 인원수로 균등 분할하고, 10원 단위 절상 후 나머지는 모집자가 부담한다.
- 모집 목표가 금액인 경우, 참여자 합계가 목표에 도달했는지 **진행바**로 표시한다.

**검증 예시** — 토스트집 / 최소주문금액 15,000원 / 배달비 3,000원 / 2명

| 참여자 | 주문 금액 | 배달비 분담 | 최종 부담금 |
|---|---:|---:|---:|
| A (모집자) | 6,000원 | 1,500원 | **7,500원** |
| B | 9,000원 | 1,500원 | **10,500원** |
| 합계 | 15,000원 | 3,000원 | 18,000원 |

혼자 주문했다면 A는 15,000원어치를 억지로 채우고 배달비 3,000원까지 부담했을 것이므로 **약 10,500원 절감**.

> ⚠️ 초기 논의에 있던 "6,000원 + 배달비 3,000원 → 2인 각 4,500원" 계산은 오류다. ① 총 6,000원으로는 최소주문금액 15,000원을 충족하지 못하고, ② 각자 먹는 음식 값이 다른데 음식 값까지 1/N 하면 실제 사용 맥락과 어긋난다.

## 9. 비기능 요구사항

### 9-1. 사용성

- 스마트폰 화면을 기준으로 먼저 설계한다.
- 주요 기능은 하단 메뉴에서 **두 번 이내의 선택**으로 접근할 수 있어야 한다.
- 모집 상태와 참여 승인 상태를 텍스트와 시각 요소로 명확히 구분한다.
- 빈 목록, 잘못된 입력, 네트워크 실패 상황에 안내 문구를 제공한다.
- 로그인 또는 위치 권한 확인에 실패해도 사용자가 원인과 재시도 방법을 알 수 있어야 한다.

### 9-2. 보안과 권한

- 비밀번호는 안전한 해시 방식(bcrypt 등)으로 저장한다.
- **DB 연결 문자열과 네이버 API 인증 정보는 소스 코드에 직접 작성하지 않고 Vercel 환경변수로 관리한다.**
- 사용자는 다른 사용자의 개인정보를 조회하거나 수정할 수 없다.
- 공동주문 수정·상태 변경, 신청 승인·거절은 **해당 모집자만** 수행할 수 있다.
- 주문 채팅은 모집자와 승인된 참여자만 열 수 있다. **권한 검사는 서버에서 수행한다.**
- 입력값 검증으로 비정상 요청과 기본적인 스크립트 삽입을 방지한다.
- **계좌번호 등 금융정보는 DB에 저장하지 않는다.** 필요 시 채팅 메시지로 직접 안내한다.

### 9-3. 데이터

- 계정·공동주문·신청 상태·채팅 메시지는 새로고침과 재로그인 후에도 유지되어야 한다.
- 날짜와 시간은 **한국 표준시(KST)** 기준으로 일관되게 표시한다. (DB는 `timestamptz` 저장)
- MVP의 활동 지역 선택지는 덕진구 생활권 안에서만 제공한다.
- 네이버 지역 검색 API·NAVER Maps API가 반환한 장소명·주소·위도·경도를 공동주문 장소 정보로 저장한다.
- **사용자의 실시간 위치나 이동 경로는 저장하지 않는다.** 거리 계산은 클라이언트에서 일회성으로 수행한다.

### 9-4. 호환성

- 최신 모바일 Safari와 Chrome에서 핵심 흐름이 정상 동작해야 한다.
- 데스크톱에서도 사용 가능하되 모바일 화면을 우선한다.

## 10. 기술 스택 및 구현 구조

### 10-1. 확정 기술 스택

| 영역 | 기술 | 역할 |
|---|---|---|
| 웹 프레임워크 | **Next.js (App Router)** | 모바일 웹 UI, 라우팅, 서버 로직 및 API 처리 |
| 데이터베이스 | **Neon DB (PostgreSQL)** | 계정·공동주문·참여 신청·채팅 메시지 영구 저장 |
| 배포 | **Vercel** | 빌드·배포, 운영 URL과 환경변수 관리 |
| 장소·주소 | **네이버 지역 검색 API · NAVER Maps API** | 가게·수령 장소 검색, 주소·좌표 변환 |
| 현재 위치 | 브라우저 Geolocation API | 사용자가 허용한 경우 현재 위도·경도 획득 |
| ORM | Drizzle ORM (권장) | 서버리스 콜드 스타트에 유리. 팀이 익숙하면 Prisma도 가능 |
| 인증 | Auth.js(NextAuth) Credentials + bcrypt | 아이디·비밀번호 단일 로그인 |
| 스타일 | Tailwind CSS | 주황/화이트 토큰을 테마 변수로 정의 |
| 개발 지원 | 생성형 AI | 코드·UI·DB 구조·테스트 초안 생성과 오류 분석 |

### 10-2. 구현 원칙

- 화면과 서버 로직은 하나의 Next.js 프로젝트 안에서 구현한다.
- **브라우저에서는 비밀번호 원문, DB 연결 문자열, 네이버 API Client Secret에 접근할 수 없어야 한다.**
- DB 읽기·쓰기는 반드시 Next.js 서버 측 로직(Route Handler / Server Action)을 통해 수행한다.
- 장소 검색은 **Next.js 서버가 네이버 지역 검색 API·NAVER Maps API를 호출**하고 필요한 결과만 클라이언트에 전달한다.
  (클라이언트에서 직접 호출하면 REST 키가 노출된다)
- 채팅은 Neon DB에 메시지를 저장하고, MVP에서는 **주기적인 새 메시지 조회(폴링)** 로 갱신한다.
- Vercel 운영 환경에서도 로컬과 동일한 핵심 흐름이 동작해야 한다.

### 10-3. 서버리스 환경에서 반드시 지킬 것 (중요)

이 스택 조합에는 **일정에 직접 영향을 주는 제약 3가지**가 있다. 착수 전에 합의하고 넘어간다.

**① 실시간 채팅에 WebSocket을 쓸 수 없다**

Vercel의 서버리스 함수는 오래 유지되는 소켓 연결에 적합하지 않다. 따라서 채팅은 다음 중 하나로 구현한다.

| 방식 | 난이도 | 판단 |
|---|---|---|
| **폴링 (2~3초 간격 조회)** | 낮음 | **MVP 채택.** 마지막 메시지 id 이후만 조회하면 부하도 작고 확실히 동작 |
| SSE (Route Handler 스트리밍) | 중간 | 함수 실행 시간 제한 때문에 재연결 처리 필요. 여유 있으면 업그레이드 |
| 외부 실시간 서비스 (Pusher/Ably 등) | 중간 | 무료 티어로 가능하나 외부 의존성 추가 |

> CHAT-06의 "새 메시지가 화면에 갱신된다"는 **폴링으로 충족된다.** 완료 기준을 기술 방식이 아니라 체감 동작으로 유지한다.
> 채팅방을 벗어나 있을 때는 폴링을 중단해 불필요한 DB 호출을 줄인다.

**② DB 커넥션은 반드시 풀링 문자열을 쓴다**

서버리스 함수는 요청마다 인스턴스가 뜨므로 커넥션이 급격히 늘어난다. Neon의 **pooled connection string**(PgBouncer 경유) 또는 `@neondatabase/serverless` HTTP 드라이버를 사용한다. 직접 연결 문자열을 쓰면 로컬에서는 멀쩡하다가 **배포 후 커넥션 고갈로 500 에러**가 난다.

**③ 마감 시각 자동 처리는 스케줄러 없이 한다**

ORDER-11(마감 시각 경과 시 마감 표시)을 크론으로 구현하려면 별도 설정이 필요하다. MVP에서는 **조회 시점에 판정**한다.

```sql
CASE WHEN status = 'OPEN' AND deadline < now() THEN 'CLOSED' ELSE status END
```

실제 `status` 컬럼 갱신은 모집자가 진입하거나 다음 쓰기 작업이 일어날 때 함께 처리한다.

## 11. 데이터 모델

### 11-1. 핵심 데이터 개요

| 데이터 | 저장 내용 |
|---|---|
| 사용자 | 아이디, 비밀번호 해시, 닉네임, 활동 지역 |
| 공동주문 | 작성자, 가게, 주문 내용, 목표, 마감·수령 시각, 수령 장소, 상태 |
| 참여 신청 | 공동주문, 신청자, 참여 메시지, 승인·거절 상태 |
| 채팅방 | 주문 채팅·커뮤니티 채팅 구분, 연결된 공동주문 |
| 메시지 | 채팅방, 작성자, 내용, 작성 시각 |

### 11-2. Postgres 스키마

```sql
CREATE TYPE pot_status   AS ENUM ('OPEN','CLOSED','ORDERED','CANCELED');
CREATE TYPE approval     AS ENUM ('PENDING','APPROVED','REJECTED');
CREATE TYPE room_type    AS ENUM ('ORDER','COMMUNITY');
CREATE TYPE message_type AS ENUM ('TEXT','SYSTEM');
CREATE TYPE target_type  AS ENUM ('HEADCOUNT','AMOUNT');

-- 활동 지역: 코드로 관리해 추후 목록 변경이 쉽도록 분리 (17-1 확정 필요)
CREATE TABLE zones (
  code       text PRIMARY KEY,        -- 'GUJEONGMUN', 'DORM' ...
  label      text NOT NULL,           -- '구정문 권역'
  sort_order smallint NOT NULL DEFAULT 0
);

CREATE TABLE users (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  login_id      text UNIQUE NOT NULL,          -- 아이디 (외부에 노출하지 않음)
  password_hash text NOT NULL,                 -- 평문 저장 금지
  nickname      text NOT NULL,                 -- 타인에게 보이는 이름
  zone_code     text REFERENCES zones(code),   -- 활동 지역
  created_at    timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE pots (
  id             uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  host_id        uuid NOT NULL REFERENCES users(id),
  zone_code      text NOT NULL REFERENCES zones(code),

  -- 가게 (네이버 지역 검색 API 결과)
  store_name     text NOT NULL,
  store_address  text,
  store_lat      numeric(10,7),
  store_lng      numeric(10,7),

  order_summary  text NOT NULL,                -- 음식 종류 / 주문 내용
  target_type    target_type NOT NULL,         -- 인원 목표 또는 금액 목표
  target_value   integer NOT NULL,             -- 명 또는 원
  delivery_fee   integer,                      -- P1 분담 계산용 (선택 입력)

  deadline_at    timestamptz NOT NULL,         -- 모집 마감 시각
  pickup_at      timestamptz,                  -- 주문/수령 예정 시각

  -- 수령 장소 (네이버 지역 검색 API·NAVER Maps API 결과 + 직접 설명)
  pickup_name    text NOT NULL,
  pickup_address text,
  pickup_lat     numeric(10,7),
  pickup_lng     numeric(10,7),
  pickup_note    text,

  extra_note     text,
  status         pot_status NOT NULL DEFAULT 'OPEN',
  created_at     timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX idx_pots_zone_status ON pots (zone_code, status, deadline_at);

CREATE TABLE participations (
  id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  pot_id          uuid NOT NULL REFERENCES pots(id) ON DELETE CASCADE,
  user_id         uuid NOT NULL REFERENCES users(id),
  apply_message   text,                        -- 참여 신청 시 짧은 메시지
  menu_amount     integer,                     -- P1: 분담 금액 계산용 (nullable)
  approval_status approval NOT NULL DEFAULT 'PENDING',
  created_at      timestamptz NOT NULL DEFAULT now(),
  UNIQUE (pot_id, user_id)                     -- 중복 신청 방지
);
CREATE INDEX idx_participations_user ON participations (user_id, created_at DESC);

CREATE TABLE chat_rooms (
  id         uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  type       room_type NOT NULL,
  pot_id     uuid UNIQUE REFERENCES pots(id) ON DELETE CASCADE,  -- ORDER일 때만
  title      text NOT NULL,                    -- COMMUNITY 고정방 이름
  created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE messages (
  id         bigserial PRIMARY KEY,            -- 폴링 커서로 사용
  room_id    uuid NOT NULL REFERENCES chat_rooms(id) ON DELETE CASCADE,
  sender_id  uuid REFERENCES users(id),        -- SYSTEM 메시지는 NULL
  type       message_type NOT NULL DEFAULT 'TEXT',
  content    text NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX idx_messages_room ON messages (room_id, id);
```

**설계 메모**

- 금액은 전부 `integer`(원 단위). 부동소수점을 쓰면 분담 계산에서 오차가 난다.
- `messages.id`를 `bigserial`로 둔 이유는 폴링 시 `WHERE room_id = $1 AND id > $2`로 **증분 조회**하기 위함이다.
- 주문 채팅과 커뮤니티 채팅을 `chat_rooms` 하나로 통합해 메시지 로직을 한 번만 구현한다.
- 모집자 본인도 `participations`에 `APPROVED` 행으로 넣으면 인원 계산과 채팅 권한 검사가 단순해진다.
- **계좌 정보 컬럼은 두지 않는다.** 금융정보 보관 리스크를 피하고, 정산 안내는 채팅 메시지로 처리한다.
- `zones`를 테이블로 분리한 이유는 활동 지역 목록이 아직 확정되지 않았기 때문이다 (17-1).

## 12. 하지 않을 것

MVP에서는 다음 기능을 만들지 않는다.

- iOS·Android 네이티브 앱
- 서비스 내 결제, 송금, 예치금 보관, 자동 정산
- 배달앱의 주문·결제 시스템 직접 연동
- 사용자의 실시간·백그라운드 위치 추적
- 사용자의 현재 정확한 위치를 다른 회원에게 공개하는 기능
- 덕진구 밖의 전국·다지역 서비스
- 사용자가 공개 커뮤니티 채팅방을 직접 생성하는 기능
- 사용자 대상 AI 음식 추천 또는 AI 자동 매칭
- 전북대 재학·소속 여부를 확인하는 학교 인증
- 휴대전화·이메일 인증 및 SMS 발송
- 비밀번호 찾기·자동 재설정
- 배달기사·식당용 별도 계정과 관리 시스템
- 고도화된 평점·등급·포인트·쿠폰 시스템
- 푸시 알림 (앱 내 배지 표시로 대체)

> 실제 음식 주문과 금액 정산은 모집자와 참여자가 주문 채팅에서 합의한 뒤 외부 수단으로 진행한다.
> 이 MVP의 책임 범위는 **사람을 연결하고 주문 조율 공간을 제공하는 것까지**다.

## 13. 완료 기준

MVP는 화면만 연결된 프로토타입이 아니라, **서로 다른 계정이 실제 데이터로 아래 흐름을 끝까지 수행할 수 있을 때** 완료된 것으로 본다.

### 13-1. 필수 사용자 시나리오

- [ ] 사용자 A와 B가 각각 다른 아이디로 회원가입하고 로그인할 수 있다
- [ ] 이미 가입한 아이디로는 추가 계정을 만들 수 없다
- [ ] A가 덕진구 내 공동주문 모집글을 작성할 수 있다
- [ ] A가 네이버 지역 검색 API·NAVER Maps API로 가게와 수령 장소를 검색해 모집글에 등록할 수 있다
- [ ] B가 목록에서 해당 글을 찾고 참여 메시지와 함께 신청할 수 있다
- [ ] A가 B의 신청을 승인 또는 거절할 수 있다
- [ ] 승인된 B는 주문 채팅방에 입장해 메시지를 보낼 수 있다
- [ ] **승인되지 않은 계정은 URL을 직접 입력해도 해당 채팅방에 접근할 수 없다**
- [ ] A가 모집을 마감하고 주문을 완료 처리할 수 있다
- [ ] 두 사용자가 마이페이지에서 만들거나 참여한 주문 내역과 상태를 확인할 수 있다
- [ ] 로그인 사용자가 음식 커뮤니티 고정 채팅방에서 메시지를 주고받을 수 있다
- [ ] 사용자가 마이페이지에서 닉네임과 활동 지역을 수정할 수 있다
- [ ] 사용자가 현재 비밀번호를 확인한 뒤 새 비밀번호로 변경할 수 있다

### 13-2. 품질 기준

- [ ] 공동주문 생성·참여·승인·채팅·완료 데이터가 새로고침 후에도 유지된다
- [ ] 모든 영구 데이터가 Neon DB에 저장되고 **재배포 후에도 유지**된다
- [ ] Next.js 프로젝트가 오류 없이 빌드되어 **Vercel 운영 URL**에 배포된다
- [ ] Vercel 환경변수를 통해 Neon DB와 네이버 지역 검색 API·NAVER Maps API가 정상 연결된다
- [ ] 네이버 API Client Secret이 브라우저 네트워크 탭에 노출되지 않는다
- [ ] 모바일 Safari와 Chrome에서 주요 화면이 잘리거나 겹치지 않는다
- [ ] 로그인 후 모든 화면에서 `공동주문 | 채팅 | 마이` 하단 메뉴가 일관되게 동작한다
- [ ] 필수 입력 누락, 마감된 주문 신청, 권한 없는 채팅 접근에 적절한 오류 안내가 표시된다
- [ ] 다른 사용자의 주문이나 개인정보를 임의로 수정할 수 없다
- [ ] 핵심 시나리오를 막는 치명적 오류가 없다

### 13-3. 통합 테스트

- [ ] 서로 다른 기기·브라우저 2대에서 동시 접속
- [ ] **로컬이 아닌 Vercel 프로덕션 URL**에서 전체 흐름 검증
- [ ] 한 사용자가 메시지를 보내면 다른 사용자 화면에 새로고침 없이 나타난다

## 16. MVP 이후 판단할 지표

제품 공개 후 다음 지표로 공동주문 서비스의 실제 필요성을 확인한다.

- 작성된 공동주문 수
- 공동주문 상세 조회 대비 참여 신청 비율
- 참여 신청 대비 승인 비율
- 모집글 중 실제 주문 완료까지 도달한 비율
- 가입자 중 공동주문을 만들거나 참여한 사용자 비율
- 음식 커뮤니티 재방문 사용자 비율
- 주문 1건이 모집 완료되기까지 걸린 시간

## 17. 아직 확정하지 않은 사항

개발 착수 전에 결정해야 한다. 각 항목에 제안을 함께 적는다.

### 17-1. 덕진구 내 활동 지역의 구분 단위

**제안**: 동 단위보다 **생활권 4개**가 실제 도보 수령 거리와 맞는다.

| 코드 | 라벨 | 대표 수령 장소 |
|---|---|---|
| `GUJEONGMUN` | 구정문 권역 | 구정문 앞, 원룸 건물 로비 |
| `SINJEONGMUN` | 신정문 권역 | 신정문 앞, 편의점 앞 |
| `DORM` | 기숙사 권역 | 참빛관·웅비관·평화관 입구 |
| `SADAEBUGO` | 사대부고 주변 권역 | 사대부고 정문, 단지 입구 |

덕진구 전체를 한 단위로 두면 도보 수령이 불가능한 거리의 모집글이 섞인다. `zones` 테이블로 분리해 두었으므로 목록 변경은 데이터 수정만으로 가능하다.

### 17-2. 커뮤니티 고정 채팅방의 최종 목록

**제안**: MVP는 **2개**로 시작한다. 방이 많으면 사용자가 분산되어 전부 비어 보인다.

1. `오늘 뭐 먹지 · 맛집 추천`
2. `같이 먹어요 · 음식 여행`

### 17-3. 신고와 제재 정책

**제안**: MVP에서는 기능을 만들지 않되, **운영 규칙만 문서로 정하고 문의 창구(채널)를 안내**한다. 노쇼·미정산·욕설 신고를 받아 수동으로 계정을 비활성화하는 수준이면 초기 규모에는 충분하다. 자동 제재·평점은 다음 버전.

## 18. MVP 우선순위 원칙

개발 중 선택이 필요할 때는 다음 순서로 판단한다.

1. 공동주문을 만들고 참여자를 모을 수 있는가?
2. 모집자가 참여자를 관리하고 승인된 사람끼리 대화할 수 있는가?
3. 사용자가 자신의 주문 상태를 다시 확인할 수 있는가?
4. 모바일 웹에서 과정이 단순하고 빠른가?
5. 위 네 가지와 직접 관련 없는 기능은 MVP 이후로 미룬다.

## 19. 기대 효과

- 최소주문금액·배달비 문제의 구조적 해소
- 지인이 없어도 성립하는 공동주문 — 기존 '함께주문' 대비 명확한 차별점
- 모집·승인·안내의 수동 과정을 하나의 흐름으로 통합
- 지역 단위 사용자 밀도 확보 시 자연스러운 커뮤니티 확장 기반 마련
- 검증된 웹 MVP를 기반으로 이후 네이티브 앱 확장 가능
