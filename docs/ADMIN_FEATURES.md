# 관리자 기능 정의 — MVP 범위

`docs/PRD.md` §17-3에 이미 남아있던 미해결 이슈("신고는 접수만 되고 처리하는 관리자 화면·API가 없다")를 실제로 해소하기 위한 관리자 기능을 정의한다. 이 문서는 "관리자 기능/페이지를 만든다면 무엇이 MVP 수준에서 꼭 필요한가"를 코드베이스 현황에 근거해 정리한 것이며, `docs/PRD.md`와 `docs/ADMIN_ROADMAP.md`의 근거 문서로 쓴다.

## 왜 필요한가 (현재 코드베이스 근거)

- `users.account_status`(ACTIVE/SUSPENDED/DISABLED), `reports.status`(PENDING/REVIEWING/RESOLVED/DISMISSED) 컬럼은 스키마(`lib/db/schema.ts`)에 이미 존재하지만, 이 값을 바꾸는 코드 경로가 어디에도 없다. 신고가 쌓이기만 하고 아무 조치로 이어지지 않는다.
- `account_status`는 지금 **채팅 메시지 전송 시에만** 체크된다(`app/api/rooms/[id]/messages/route.ts:56`, CHAT-15). 로그인, 참여 신청, 모집글 작성 경로에는 이 체크가 없다 — 즉 관리자가 정지 처리를 해도 그 유저는 로그인하고 새 글을 쓰고 참여 신청까지 할 수 있다. 회원 제재가 실제로 의미를 가지려면 이 구멍부터 막아야 한다.
- 부적절한 모집글(스팸, 사기성 내용 등)을 신고 없이도 운영자가 직권으로 내릴 수단이 없다.

## MVP 범위로 확정한 4개 기능

### 1. 관리자 권한 검증
- `users` 테이블에 `role`(`USER` | `ADMIN`, 기본값 `USER`) 컬럼 추가. 별도 권한 테이블/RBAC 시스템은 만들지 않는다 — 운영자가 1~2명 수준인 서비스 규모에 맞지 않는 과설계다.
- 관리자 계정 부여는 셀프서비스 없이 DB에서 직접 처리한다(가입 화면에 "관리자로 가입" 같은 옵션을 두지 않음).
- `/admin` 이하 모든 페이지는 서버 컴포넌트 레이아웃에서 세션 검사: 비로그인 → `/login`, 로그인했지만 `role !== 'ADMIN'` → `/pots`로 리다이렉트.
- `/api/admin/*` 라우트도 각 핸들러에서 동일하게 검사(페이지 레이아웃 가드는 API 라우트에 적용되지 않으므로 별도 필요).

### 2. 신고 처리 (신고함)
- 관리자가 `reports` 목록을 상태별로 조회하고(`PENDING` 우선), 신고 사유·상세 내용·메시지 스냅샷을 확인한다.
- 상태를 `REVIEWING` / `RESOLVED` / `DISMISSED`로 변경하고 `admin_note`, `reviewed_at`을 남긴다.
- 신고 상세 화면에서 바로 "신고된 유저 정지" 액션을 실행할 수 있게 해 신고 처리와 제재를 한 화면에서 잇는다.

### 3. 회원 상태 제어 (제재/정지) — 전체 경로 적용
- 관리자가 특정 유저의 `account_status`를 `ACTIVE`/`SUSPENDED`/`DISABLED`로 변경.
- **주의**: 정지 처리가 실제로 동작하려면 채팅 전송 외의 경로에도 체크를 추가해야 한다 — 로그인(`auth.ts` authorize), 참여 신청(`POST /api/pots/:id/join`), 모집글 작성(`POST /api/pots`)에 `account_status !== 'ACTIVE'` 검사를 확장한다.

### 4. 모집글 직권 삭제
- 관리자는 참여자 유무·방장 동의 여부와 무관하게 모집글을 즉시 삭제할 수 있다(부적절한 게시글 대응용 비상 조치).
- 일반 사용자용 `DELETE /api/pots/:id`(방장 전용, 참여자 0명 조건)와는 별도의 `DELETE /api/admin/pots/:id`로 분리한다 — 일반 삭제 규칙에 예외를 끼워 넣지 않고 관리자 전용 경로를 새로 둔다.

## 이번 범위에서 제외한 것 (+ 이유)

| 항목 | 제외 이유 |
|---|---|
| 마스터 데이터(카테고리=활동 지역 zone) CRUD | `CLAUDE.md`에 4개 권역이 PRD §17-1 결정으로 이미 확정·고정되어 있다고 명시됨. 관리자가 임의로 추가/삭제하게 하면 이 결정을 무력화한다. |
| 공지사항 작성/수정 | PRD 어디에도 없는 신규 기능. 지금 실제로 막혀있는 문제(신고 처리 공백)와 무관해 이번 범위에서는 다루지 않는다. |
| 신고/제재 이력에 대한 별도 감사 로그(audit log) 테이블 | `reports.admin_note` + `reviewed_at`으로 신고 기반 조치는 이미 추적 가능. 신고와 무관한 직권 삭제까지 별도 로그 테이블을 만드는 건 이번 MVP 바(bar)를 넘는 범위 — 필요해지면 후속 과제로 남긴다. |
| 관리자 초대/역할 관리 UI | 운영자가 소수(1~2명)인 단계에서는 DB로 직접 `role`을 바꾸는 것으로 충분하다. |

## 관리자 화면 IA

- `/admin` — 랜딩(신고함/모집글 관리/회원 관리로 이동하는 진입점)
- `/admin/reports` — 신고 목록 + 상세 + 상태 변경 + 유저 정지 액션
- `/admin/pots` — 전체 모집글 목록(zone 무관) + 직권 삭제
- `/admin/users` — 전체 회원 검색 + 계정 상태(`ACTIVE`/`SUSPENDED`) 변경. 신고 없이도 임의 회원을 정지/정상화할 수 있는 독립 화면 (2026-07-30 추가 — `PATCH /api/admin/users/:id`는 이미 범용으로 만들어져 있었는데 이걸 호출하는 독립 페이지가 빠져 있었음)

## API 추가 목록

| 메서드 | 경로 | 설명 | 권한 |
|---|---|---|---|
| PATCH | `/api/admin/reports/:id` | 신고 상태·메모 변경 | 관리자 |
| PATCH | `/api/admin/users/:id` | 계정 상태(`account_status`) 변경 | 관리자 |
| DELETE | `/api/admin/pots/:id` | 모집글 직권 삭제 (참여자/방장 조건 무시) | 관리자 |

> 신고 목록·전체 모집글 목록 조회는 별도 REST 엔드포인트를 두지 않는다. `/admin/reports`·`/admin/pots` 페이지(서버 컴포넌트)가 각각 `lib/admin/data.ts`의 조회 함수, 기존 `lib/server-data.ts`의 `listPots()`(필터 없이 호출하면 이미 zone 무관 전체 목록)를 직접 호출해 초기 데이터를 받고, 검색은 클라이언트에서 필터링, 변경 후에는 `router.refresh()`로 다시 조회한다 — `lib/api.ts`(클라이언트)와 `lib/server-data.ts`(서버 컴포넌트)를 분리한 이 프로젝트의 기존 관례와 동일하다.
